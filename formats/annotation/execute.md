# Annotation Format — Implementation SOP

## Reference examples (look here first)

To find examples, look in the shared `../../files/` folder for any file whose name contains `vf=annotation`.

## What this format is

A printed page of copy being marked up by hand (highlighter circles, underlines) as the video reads it. It works because the physical act of marking up real printed copy as it's read makes the argument feel like evidence being highlighted for the viewer, not a pitch being delivered.

Strongest for **claims-heavy or script-heavy arguments**, where seeing the copy underlined paces the viewer through a longer argument.

The one property to protect: **the page has to be real and printed, and the markup has to happen live, in sync with the voiceover reading it.** Draw the writing from scratch instead of marking up printed copy and it becomes a different format (`whiteboard`), not Annotation.

## Inputs

Expect a **messaging angle** — the script or claim copy to print and mark up. The angle supplies the words; this SOP governs the paper, the markup pacing, and the camera.

## Anatomy

1. **The printed page:** a document of copy filling most of the frame.
2. **The markup:** hand-applied highlighter circles or underlines, live.
3. **The pacing:** markup synced with a voiceover reading the page.
4. **CTA/offer close.**

### Beats (in order)
1. The page fills the frame.
2. The hand marks up the line being read, in the order the voiceover says it.
3. The markup lands on the final key line or offer as the voiceover closes.

## Build rules (priority order)
1. **Print the script or claim page for real**; the paper texture sells it.
2. **Highlight only the lines that carry the argument**, in the order the voiceover says them.
3. **Keep it top-down and steady** so the page stays readable.
4. **Keep it to one message, one offer or CTA.**
5. **Honest claims.** No absolutes or banned phrases.

## Length caps

| Element | Cap |
|---|---|
| Highlighted lines | only the lines carrying the argument |
| Offer/CTA | 1 |

## Build steps

1. Read the brief: the script or claim copy to annotate.
2. Print the page for real.
3. Plan which lines to highlight, in the order the voiceover will say them.
4. Shoot top-down and steady, hand marking up each line in sync with the voiceover.
5. Claims pass: claims specific and validated, no absolutes or banned phrases.
6. Legibility check: confirm it reads at a glance on a phone.
7. Deliver: printed-page copy, highlight/markup order, voiceover script, claims flags.

## QA checklist
- [ ] A real printed page of copy fills most of the frame
- [ ] Markup happens live, in sync with the voiceover reading it
- [ ] The device carries the message
- [ ] It reads at a glance on a phone
- [ ] Honest claims; no absolutes or banned phrases
